# Kashimi SDK

Kashimi API client, generated from the OpenAPI spec.

Kashimi is an open-banking API for account-to-account payments: one API to hundreds of banks.

Learn more about Kashimi API at [www.kashimi.tech](https://www.kashimi.tech).

This is an unofficial SDK for the Kashimi public API, generated by Voxgig with [`@voxgig/sdkgen`](https://github.com/voxgig/sdkgen). It is not affiliated with, endorsed by, or sponsored by the upstream API provider.

## About Kashimi API

**Credentials.** Kashimi uses OAuth 2.0 client credentials. Exchange your client ID
and secret for an access token, valid for 30 minutes, then pass the token as the `apikey`
option:

```ts
import { KashimiSDK } from '@voxgig-sdk/kashimi-sdk'

// The Sandbox. Without `base` the SDK calls Production, https://api.kashimi.tech.
const base = 'https://api-sandbox.kashimi.tech'

// The token call is form-encoded, with HTTP Basic credentials: the conform
// feature sends it that way. The generated TokenCreateData type also requires
// the response's fields, hence the cast.
const auth = new KashimiSDK({ base, feature: { conform: { active: true } } })
const basic = Buffer.from(
  `${process.env.KASHIMI_CLIENT_ID}:${process.env.KASHIMI_CLIENT_SECRET}`).toString('base64')
const token = await auth.Token().create({
  grant_type: 'client_credentials',
  scope: 'payments:read payments:write providers:read',
  authorization: 'Basic ' + basic,
} as any)

// Every other call sends the token as `Authorization: Bearer <token>`.
const apikey = token.data().access_token
const client = new KashimiSDK({ base, apikey })

const providers = await client.Provider().list()
const payment = await client.Payment().load({ id: 'your-payment-id' })
console.log(payment.data())
```

The same exchange with curl:

```bash
curl --request POST "https://api-sandbox.kashimi.tech/api/v1/auth/token" \
  --user "$KASHIMI_CLIENT_ID:$KASHIMI_CLIENT_SECRET" \
  --data-urlencode "grant_type=client_credentials" \
  --data-urlencode "scope=payments:read payments:write providers:read"
```

**The conform feature.** Kashimi's token call takes a form-encoded body and HTTP Basic
credentials. A generated SDK sends JSON with the client's bearer token, so this repository
adds a `conform` feature, from its own sdkgen package in `ext/`. It sends a form-encoded
body as the definition declares, and keeps a credential the call passes itself. Like every
SDK feature, it is off until you turn it on.

**Scope.** Every operation in Kashimi's published definition is here except the three it
tags "Internal Endpoints". The `callback`, `client_jwk`, `sender_account`,
`psu_provided_data`, `sca_method`, `sca_data`, `confirmation_data` and
`consent_status` entities are the routes of Kashimi's hosted payment flow.
`Country().list()` returns one entity per country, and each entity's data is the bare
country code, such as `'DE'`.

## Entities, not endpoints

This SDK exposes the API as **18 semantic entities** that you
call directly, instead of assembling URL paths and query strings. See the [Entities](#entities) table below for the full list. Entities are
**Capitalised** to mark them as the primary surface, each with the operations they
support (`list`, `load`, `create`, `update`):

```ts
const client = new KashimiSDK()
const callback = await client.Callback().load({ provider_id: "example", state: "example" })
```

Thinking in entities keeps the mental model small — for people and AI agents alike —
rather than reasoning about raw HTTP routes and query parameters.

## Offline unit testing

Every SDK ships a built-in **test mode** that swaps the HTTP transport for
an in-memory mock, so your unit tests run fully offline — no server, no
network, and no credentials:

### TypeScript

```ts
// The offline mock starts EMPTY — seed it with the records the test needs.
// Shape: { entity: { <entity-name>: { <id>: <record> } } }
const client = KashimiSDK.test({
  entity: {
    client_jwk: {
      test01: { id: 'test01' },
    },
  },
})
const clientjwk = await client.ClientJwk().load({ client_id: 'example_client_id', provider_id: 'example_provider_id' })
// clientjwk is the ClientJwk entity; .data() reads its mock record
console.log(clientjwk.data())
```

### Python

```python
client = KashimiSDK.test()
clientjwk = client.ClientJwk().load({"client_id": "example", "provider_id": "example"})
print(clientjwk.data_get())
```

### PHP

```php
// Seed fixture data so offline calls resolve without a live server.
$client = KashimiSDK::test([
    "entity" => ["client_jwk" => ["test01" => []]],
]);
$clientjwk = $client->ClientJwk()->load(["client_id" => "example", "provider_id" => "example"]);
```

### Golang

```go
client := sdk.Test()
result, err := client.ClientJwk(nil).Load(
    map[string]any{"client_id": "example", "provider_id": "example"}, nil,
)
```

### Ruby

```ruby
  "entity" => { "client_jwk" => { "test01" => {} } },
```

### Lua


## Use it from an AI agent (MCP)

The generated MCP server exposes this SDK's list and load operations as
[MCP](https://modelcontextprotocol.io) tools that Claude, Cursor or Cline
can call directly. It only reads: create, update, patch and remove become tools when the SDK's model sets
`main: kit: target: 'go-mcp': tool: write: true`. Build and register it:

```bash
cd go-mcp && go build -o kashimi-mcp .
```

Then add it to your agent's MCP config (Claude Desktop, Cursor, etc.):

```json
{
  "mcpServers": {
    "kashimi": {
      "command": "/abs/path/to/kashimi-mcp"
    }
  }
}
```

## Entities

The API exposes 18 entities:

| Entity | Description | API path |
| --- | --- | --- |
| **Callback** | The bank redirect back into the hosted payment flow. | `/api/v1/ob/callbacks` |
| **ClientJwk** | The JSON Web Key Set of a client at a provider. | `/api/v1/ob/client-jwks` |
| **ConfirmationData** | The confirmation data of a decoupled payment. | `/api/v1/ob/payments/decoupled/confirmation-data` |
| **ConsentStatus** | The consent status of a decoupled payment. | `/api/v1/ob/payments/decoupled/consent-status` |
| **Country** | A country where Kashimi supports payment providers. | `/api/v1/capabilities/providers/countries` |
| **Followup** | A follow-up for a payment, created at its provider. | `/api/v1/ob/payments/{paymentId}/followups` |
| **Healthcheck** | The status of the API. | `/api/status` |
| **HostedUiCustomization** | The customizations of the hosted payment UI for a client. | `/api/v1/capabilities/clients/{clientId}/hosted-ui-customizations` |
| **Payment** | A bank payment: initiate one, list yours, load one by id, or cancel one in the hosted flow. | `/api/v1/archive/payments` |
| **PaymentStatus** | The status of a payment: its full history, or the latest. | `/api/v1/archive/payment-statuses` |
| **Provider** | A bank or payment provider, with its supported payment schemes and required fields. | `/api/v1/capabilities/providers` |
| **PsuProvidedData** | Data the payer provides in the hosted payment flow. | `/api/v1/ob/payments/psu-provided-data` |
| **Report** | A reporting summary of one payment: amount, status, provider, sender, recipient and remittance information. | `/api/v1/reports/payments/{id}` |
| **ScaData** | The strong customer authentication data of a decoupled payment. | `/api/v1/ob/payments/decoupled/sca-data` |
| **ScaMethod** | The strong customer authentication methods of a decoupled payment, and the one chosen. | `/api/v1/ob/payments/decoupled/sca-methods` |
| **SenderAccount** | The sender accounts offered in the hosted payment flow, and the one chosen. | `/api/v1/ob/payments/sender-accounts` |
| **Subsidiary** | A regional or subsidiary institution of a provider. | `/api/v1/capabilities/providers/{id}/subsidiaries` |
| **Token** | A short-lived access token, issued for your client credentials. | `/api/v1/auth/token` |

The operations available across these entities are **load**, **list**, **create**, **update** — see each entity's
own list above for exactly which it supports.

## Direct and prepare

For endpoints the entity model doesn't cover, use the low-level methods:

- **`direct(fetchargs)`** — build and send an HTTP request in one step.
- **`prepare(fetchargs)`** — build the request without sending it.

Both accept a map with `path`, `method`, `params`, `query`,
`headers`, and `body`. See the [How-to guides](#how-to-guides) below.

## Advanced

> Everyday use only needs the sections above. This explains the internals
> behind every call — relevant when writing custom features.

Every SDK call runs the same five-stage pipeline:

1. **Point** — resolve the API endpoint from the operation definition.
2. **Spec** — build the HTTP specification (URL, method, headers, body).
3. **Request** — send the HTTP request.
4. **Response** — receive and parse the response.
5. **Result** — extract the result data for the caller.

A feature hook fires at each stage (e.g. `PrePoint`, `PreSpec`,
`PreRequest`), so features can inspect or modify the pipeline without
forking the SDK.

## Customizing this SDK

This repository contains its own generator (`.sdk/`), so the SDK is
customizable without forking any upstream tool:

- **The model** (`.sdk/model/`) is what generation reads: the API's
  entities and operations, the targets, the features, and this project's
  own settings. It is written in [aontu](https://aontu.dev), a JSON-based
  specification language designed for building ontologies: easy to edit
  by hand, and files unify rather than override, so small declarations
  compose into one model. Regeneration re-reads it every time.
- **Templates** (`.sdk/tm/`) and **components** (`.sdk/src/cmp/`) are
  the two layers of generation, copied into this repo: templates are the
  literal per-language source, components generate the API-shaped parts.
- **Regeneration overwrites.** Each run rewrites every generated file from
  the model, the templates and the components, so an edit made to
  generated output is lost. Say what this project needs in its own model
  (`.sdk/model/project.aontu`), or extend a target with a component of its
  own in `.sdk/src/cmp/<target>/`, registered with `registerComponent`,
  which `voxgig-sdkgen doctor` reports as an addition rather than drift.
- **Custom features and entire custom targets** arrive through sdkgen
  packages (`voxgig-sdkgen package add`), on the same rails as the
  bundled languages, and `voxgig-sdkgen doctor` reports any drift from
  what a resync would write.

### Project map

| Path | What it holds | Edit it? |
| --- | --- | --- |
| `.sdk/model/project.aontu` | This project's own decisions: package names, versions, features and per-target settings | Yes. The scaffold writes it once and never again. |
| `.sdk/model/text.aontu` | The README wording, in `main.kit.text`: the tagline, the summary and the entity descriptions | Yes. The scaffold writes it once and never again. |
| `.sdk/model/guide/guide.aontu` | How the spec's paths map onto entities and operations | Yes. The scaffold writes it once and never again. |
| `.sdk/model/`, the rest | The API model built from the spec, and the target and feature definitions | Not by hand. Generation, `target add` and a new scaffold run rewrite it. |
| `.sdk/def/` | The OpenAPI spec | Replace it when the API changes. Generation rebuilds the model from it. |
| `.sdk/src/cmp/<target>/`, `.sdk/tm/<target>/` | The components and templates that generate each target | Only to add a component of your own. `target add` overwrites the copies. |
| `.sdk/test/` | The shared test cases the generated tests run | No. |
| `<target>/`, such as `ts/` | One generated SDK per target, with its own tests | No. Generation overwrites it. |
| `README.md`, `LICENSE`, `Makefile` and the other root files | The repository's generated files | No. Generation overwrites them. |

### Common commands

Run these from `.sdk/`:

```bash
npm run generate               # regenerate every target from the model
npm run add-target <target>    # add a target, or resync one after an sdkgen update
npm run add-feature <feature>  # add a feature to every target
npx voxgig-sdkgen doctor       # report where .sdk/ differs from what a resync writes
```

In an SDK directory, `make test` runs that SDK's tests.
